# Working on the design system

This repo is a shared design system. Apps copy `dist/` into their own repo and use nothing else from here.

## Rules

- `dist/` is generated. Never edit a file in it by hand. Change the source, run `npm run build`, and commit the source and the regenerated `dist/` together.
- `tokens/tokens.css` is the single source for tokens. The Tailwind preset, the token data file, the design token block and the manifest are all derived from it by `scripts/build.mjs`.
- `themes/<name>.css` is a theme, written by hand: values for existing token names in light and dark, in the selector shape of `tokens/tokens.css`, inside `@layer ds.theme`, which the layer order puts after `ds.tokens`. "Default mode: dark" in its first comment makes a page with no `data-theme` dark. The build fails, naming the theme, when it adds a name, lacks a mode, sets for light alone a colour the default sets in both, or fails a pair in `tokens/pairs.json` in either mode with its values resolved over the default ones. It writes `dist/themes/<name>.css`, `.design-tokens.md`, `.tokens.json` and `.json`. The Tailwind preset has nothing per theme.
- A theme that does not set a token takes the default theme's value for it, and every pair is checked against each theme, so a new token or a new pair can fail a theme's build. Give the theme a value then.
- The token vocabulary is closed. Do not add a token name to solve a local problem. A theme changes values only.
- There is one interactive colour, `--ds-color-accent`: it is used for the primary action, focus, selection and active work, and never for a status that is not "working". `--ds-color-focus` and `--ds-color-info` are tokens of their own that a theme may give the same value. The approval tone is a small signal for what waits on a person, never a band of background.
- A surface has one of four levels: `--ds-color-surface` the page, `--ds-color-surface-pane` a pane of the app shell, `--ds-color-surface-raised` a card or a control above the page, `--ds-color-surface-sunken` a well. The pane surface is for the sidebar nav, the inspector and the tab bar, each with a hairline that stays drawn in dark, and a test fails when anything else takes it.
- Density is four tokens, `--ds-size-control`, `--ds-size-row`, `--ds-text-ui` and `--ds-leading-ui`. `:root` holds the default: a 40px control, a 40px row and 15px body text on a 23px line. `data-ds-density="compact"` on a container, the one value of the attribute, sets them to 32px, 36px and the metadata size and line height, through the one density block at the end of `tokens/tokens.css`. The last block, under `@media (pointer: coarse)`, makes the control and the row 44px on every element, a compact container included, and makes each type size one pixel larger, written out in rem, with two exceptions: `--ds-text-md` is the body size there, and `--ds-text-2xl` is left out and stays. The build fails when the compact block sets anything else, when another value of the attribute has a block, when the control or the row of a coarse pointer differs from `--ds-size-touch`, when a coarse-pointer type size is not what that rule gives, and when a theme sets a density token. It writes the three sets of values, default, compact and coarse-pointer, to `dist/manifest.json`, `dist/tokens.json` and `dist/design-tokens.md`.
- Type is seven roles: `--ds-text-xs` (12px), `-sm` (13), `-md` (14), `-ui` (15), `-lg` (16), `-xl` (20) and `-2xl` (28), with `--ds-text-mono` for a block of code. Each is in rem, so it follows the reader's font size, and has a `--ds-leading-` token of the same name; `lg`, `xl` and `2xl` have a `--ds-tracking-` token too, set wherever that size is a role's text. Nothing is under 12px: the build fails on a type size under 0.75rem or not in rem, and a test fails on text set in capitals. The label over a group is 13px semibold in sentence case with no tracking. Code inside a sentence is `0.93em`, the one length `base/typography.css` writes out. `docs/authoring.md` has the role each kind of text takes: follow it, and add a row there when a new kind of text appears.
- Spacing is 4, 8, 12, 16, 24, 32 and 48px (`--ds-space-xs` to `--ds-space-3xl`), with three steps between that components use: 2px (`-2xs`), 6px (`-xs-sm`) and 20px (`-lg-xl`). Radius is `--ds-radius-xs` (6px, a tag), `-sm` (10px, a control), `-md` (12px, a card), `-lg` (16px, a dialog, a sheet or the composer box) and `-full`, which is for the shapes `docs/authoring.md` lists and nothing else. A box inside another takes the step under it. A test holds each component to its radius and each use of the pill to the list.
- A theme sets colours, the two font stacks and the shadow. It cannot set a type size, a line height, a tracking or a radius: the build fails, naming the theme and the token.
- A pointer target is at least 44px each way on a coarse pointer and 24px on a fine one: the 44px rule is for coarse pointers. A component takes the height of a control from `--ds-size-control` and of a row from `--ds-size-row`, a fixed size from `--ds-size-control-xs` (24px), `-sm` (28px), `-md` (32px, a small control) or `-lg` (48px), and uses `--ds-size-touch` only for the hit area of a control drawn smaller, inside `@media (pointer: coarse)`. A test fails on any other use.
- Every custom property starts with `--ds-` and every class starts with `ds-`.
- Colour tokens are six-digit hex. No `rgb()`, `oklch()`, `color-mix()` or `light-dark()` in a colour token, because consumers parse computed values as `#rrggbb`.
- A dark value goes in both the `[data-theme="dark"]` block and the `[data-theme="auto"]` block. The build fails if the two differ.
- A new text and background combination needs an entry in `tokens/pairs.json`. The build fails when a text pair is below 4.5:1 or a `ui` pair is below 3:1, in either mode, for the default theme and for every theme in `themes/`. An entry may carry `"themes": ["<name>"]`: it is then checked for those themes only. Use that for a combination one theme holds and the default theme does not, never to get a component past the gate: a component relies only on a pair with no list.
- The badge's `statusSet` in `meta.json` is the one icon and tone for each state of a run. `run-status`, `run-timeline`, `check-list`, `tool-call`, `step-group` and `now-doing` draw a state of that set with its icon and tone, and a test checks it. Change the set there and in those components together.
- The breakpoints are 768px, 1024px and 1280px: `--ds-breakpoint`, `-lg` and `-xl`, the Tailwind variants `md:`, `lg:` and `xl:`, and the three widths the checker's `off-breakpoint` rule allows in a media query. A custom property cannot be used in a media query, so write the number there. A component uses 768px alone; 1024px and 1280px are for the panes of a screen, so only a page pattern uses them, and a test checks both. A container query may use any width.
- `base/` holds the reset, typography, layout primitives, the visually hidden class, focus ring, fonts and icons. The build bundles them with the tokens into `dist/design-system.css` and copies fonts and icons into `dist/`.
- `components/<name>/` is one component: `<name>.css`, `examples.html` and `meta.json`, all written by hand. `docs/authoring.md` is the contract for them. Read it before adding or changing a component.
- `patterns/<name>/` is one page pattern: a whole screen composed from components, such as a settings page. It holds the same three files as a component, built to the same contract, with `"kind": "pattern"` in `meta.json` and only the layout CSS the screen needs. A pattern cannot take the name of a component.
- The build bundles pattern styles after every component, lists patterns in the `patterns` array of `dist/components.json` (the `components` array holds components only), adds their classes to the manifest and gives each a gallery page whose examples run in one column. It also writes `dist/components-index.json`, the short list an agent reads first: name, kind, title, purpose, status and classes of every component and pattern. The gallery index lists patterns after components.
- To add a component, add its folder and nothing else. The build puts it in `dist/design-system.css`, `dist/components.json`, the manifest's class list and the gallery, and fails, naming the folder, if the folder breaks the contract.
- Component styles key off native state and ARIA attributes, never off a class a script would toggle. No component uses an inline `style` attribute.
- A component whose state has no native or ARIA form takes it from a `data-state` attribute the app sets, with the values listed in its metadata: a tool call's lifecycle, a streaming message, a station of a run. The examples of such a state carry the same value in the wrapper's `data-state`. Every label is app text in the markup, never in the stylesheet.
- No behaviour module opens or closes a step group. The rule is the app's to apply, and the step group's metadata states it.
- The gallery script moves the start of every `<ds-elapsed>` in an example by the time since the instant the examples were written at, and the browser tests hold the clock still, so a time that counts up reads the same in every screenshot. Write an example's `datetime` a little before 2026-11-22T10:00:00Z.
- `gallery/` holds the gallery's own stylesheet and script. They select by element and `data-gallery` attribute, use token values only, and are not part of the system. `?theme=dark` sets the mode and `?brand=<name>` loads a theme from `dist/themes/`.
- `behaviors/` holds the optional scripts the system ships, copied to `dist/behaviors/`. Each is a single ES module with no dependencies that defines one element for an app without a framework: `tabs.js` defines `<ds-tabs>`, `combobox.js` defines `<ds-combobox>`, `command-palette.js` defines `<ds-command-palette>`, `elapsed.js` defines `<ds-elapsed>`, `transcript.js` defines `<ds-transcript>`, `menu.js` defines `<ds-menu>` and `listbox.js` defines `<ds-listbox>`. A framework app loads none of them and sets the same ARIA attributes itself. A module sets attributes and moves focus only, never a class or an inline style, and is harmless when loaded twice. A module decides from the state of the page as it is when an event arrives, not from a flag it stored. Four modules also write text, always in words the app gave them in the markup: `<ds-elapsed>` writes the time, `<ds-transcript>` the count of new rows, `<ds-combobox>` the count of matches into its status line, and `<ds-command-palette>` the no-match sentence from `data-ds-empty` into its status element, which stays in the page and is never hidden, so a screen reader hears it. No other module writes text. `<ds-transcript>` also sets the scroll position. Every gallery page loads every module in `behaviors/`, in alphabetical order.
- `react/` holds the React source the system ships, copied to `dist/react/` and never compiled here, one file per piece: `busy-button.tsx`, `dialog.tsx` (the dialog, the confirm dialog and the sheet), `approval.tsx`, `use-menu.ts`, which gives a menu the keyboard of `behaviors/menu.js`, and `use-transcript.ts`, which follows a transcript by the same rule as `behaviors/transcript.js`. Change a hook and its module together. Each file depends on React and on the other files there only, renders the component's classes and ARIA exactly as its `examples.html` does, never a class of its own or an inline style, and takes the words a reader sees or hears from the app's props, with defaults only for words the component's metadata fixes, such as Allow and Decline. A hook follows the rules of a behaviour module: it decides from the state of the page when an event arrives, and sets attributes and moves focus only. Types use discriminated unions where a combination of props would be invalid, `ComponentPropsWithRef` for an element's native props, and no `any`. Add a file only for a pattern an app has been seen to write by hand; `test/fixtures/react-source/` typechecks each one in strict use and renders it for the browser tests in `test/visual/react-source.spec.mjs` and `test/visual/react-layer.spec.mjs`.
- `checker/` is the checker, shipped as source in `dist/checker/`. It has no dependencies.
- `scripts/migrate-prefix.mjs` is the codemod that moves an app from the `gw` prefix of 0.5 to `ds`. The build copies it to `dist/migrate-prefix.mjs`. It has no dependencies. The checker's `old-prefix` rule reports a name that still has the old prefix.
- The build reads every rule ID out of the checker's source into the `rules` list of `dist/manifest.json`. It finds an ID written as `id: "…"`, `rule: "…"`, `add(line, "…")` or `scaleCategory("…")`, so write a new rule's ID in one of those forms.
- `rules/` holds the rules an app's agents read, written by hand and copied to `dist/rules/`. `rules/core.md` is the one file every agent reads, and the build fails when it is longer than 2,400 characters. Put detail in the longer files and point to them from `core.md`.
- Every rule ID the checker can report has a row in `rules/checker-rules.md`: the ID, what it means and the fix. Add the row with the rule.
- In a rules file, a code span holding one lower-case word names a component, a checker rule, a system class or a `data-` or `aria-` attribute, and a test checks that each exists. `rules/choosing-components.md` names every component and every pattern, so add a new one there.
- `hooks/` holds the optional Claude Code hook and its example settings, copied to `dist/hooks/`.
- `scripts/sync.mjs` copies `dist/` into an app and writes `hashes.json` there. On an update it prints the components, patterns and rules that were added, changed or removed. `docs/consumer-guide.md` is how an app adopts the system. A test sets up an app from the commands and files in that guide, so keep its code blocks exact.
- The build copies `LICENSE` and `NOTICE` into `dist/`, so a vendored copy carries them.
- The version is the `version` in `package.json`, which the build writes to `dist/VERSION`. A release raises it and adds an entry to `CHANGELOG.md`.
- A structural rule is a function over a document tree in `checker/rules/`. It takes the tree and an options object, which holds the app's class prefix when one is known. It must run unchanged on a parsed HTML file and in a browser, so it uses only the tree helpers in `checker/rules/tree.mjs`, never `node:` modules or the DOM. The build joins the files listed in `DOM_BUNDLE` in `scripts/build.mjs` into `dist/check-dom.js`: add a new rule file to that list, and keep top-level names unique across those files.
- No runtime dependencies in the stylesheet, the tokens, the checker, the behaviour modules or the build. A file in `react/` may import a client dependency that is a row in the table of Botbench's ADR 0011 and is named in `docs/adr/0001`; the app installs it. Development dependencies are for tests (React, those client dependencies and esbuild only build a test fixture) and for `npm run vendor`, which copies font and icon files from `node_modules` into `base/`. The build never reads `node_modules`.
- Node 24, ES modules. Tests use `node --test`.

## Commands

- `npm run build` regenerates `dist/` and prints the contrast report.
- `npm run test:visual` runs the browser tests in the installed Chrome, including the structural rules on rendered pages. For the gallery it opens the 390px pages with a coarse pointer, as a phone has, and the 1280px pages with a fine one, runs axe, measures pointer targets (44px each way on the coarse pointer, 24px on the fine one) and compares every page with its committed screenshot in `test/visual/screenshots/`, `<page>-<width>-<mode>.png`, failing on a difference of more than 20 pixels. A fixed list of pages is also shot under the Botbench theme, named `<page>-<width>-<mode>-botbench.png`. The screenshots are taken in `test/visual/page-screenshots.mjs`, once for each width: Chrome drops an emulated touch screen while it captures a whole page, so for 390px it is started with a coarse pointer of its own, and a test reads the committed screenshot of the button page and fails when the button in it is not 44px tall at 390px or 40px at 1280px. It never writes a screenshot.
- `npm run test:visual:update` runs the same tests and rewrites the screenshots that differ, and writes missing ones. Run it only for a change you mean, look at every rewritten file, and commit them with the change. An update of Chrome or Playwright is the one other event expected to change them: rewrite them then, in a commit of their own. It does not delete the screenshot of a page that no longer exists.
- `npm run test:visual:webkit` and `npm run test:visual:firefox` run, in Playwright's WebKit and Firefox, the gallery tests tagged `@engines` (axe, the structural rules and the pointer targets at 390px with a coarse pointer and at 1280px with a fine one, for the components a Botbench user meets) and the spec files listed in `playwright.config.mjs`. Install the engines once with `npx playwright install webkit firefox`. Neither takes screenshots, and a test that forces a state through Chrome's debugging protocol stays in Chrome. Results are in `docs/browser-support.md`.
- `npm test` runs the tests. One of them rebuilds into a temporary directory and fails, naming the file, if the committed `dist/` is stale.

Before finishing, run `npm run build` and then `npm test`. After changing a component or the gallery, run `npm run test:visual` too. If it fails on a screenshot you meant to change, run `npm run test:visual:update` and look at the screenshots it rewrote. After changing a component a phone user meets, or a behaviour module, run `npm run test:visual:webkit` as well. `git status` must show no change in `dist/` that you have not accounted for.
